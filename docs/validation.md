# Validation status

This page records what has actually been exercised, and where. It is the only
page that grades a capability against the real exchange: a product may not be
named in the **Mainnet** column of the
[feature support matrix](../README.md#feature-support-matrix) unless a row below
records the run that put it there, and no page may call anything **Stable**
while this one does not — [why](#why-nothing-is-marked-stable) is at the bottom.

## The evidence ladder

One vocabulary is used on this page, and every cell in the tables below carries
exactly one rung of it. A rung is earned by a record that can be pointed at, not
by confidence.

This is also the project's **only** status vocabulary. No other page may define
a scale of its own: a page that needs to grade a capability takes a rung from
this table and links back to this section, so that one word means one thing
across the documentation.

| Rung                  | What it means                                                                                                                                                                                                                                                                                                            |
|-----------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **implemented**       | The code path exists and has been read. Nothing asserts that it behaves as described                                                                                                                                                                                                                                     |
| **unit-tested**       | The offline suite asserts the behavior against recorded or synthetic venue payloads, one call or one payload at a time. This is the adapter agreeing with its authors                                                                                                                                                    |
| **offline-harness**   | The behavior was driven as a *sequence* through the execution harness (`ExecHarness` in `tests/test_execution_orders.py`): the platform's own `Cache`, `MessageBus`, `OrderFactory` and `Order` state machine, a real `LiveExecutionEngine` where the engine's own conduct is at stake, and every REST namespace stubbed |
| **mainnet-confirmed** | A run against Gate.io mainnet did the thing, and what that run checked is written down under [Mainnet validation results](#mainnet-validation-results)                                                                                                                                                                   |

The three lower rungs answer the same question — does the adapter do what its
authors intended — with increasing severity. Only the fourth answers a different
one: whether Gate.io agrees. **Anything below *mainnet-confirmed* means the
venue has never seen that path.**

What separates the third rung from the second is what gets asserted, not how
much machinery is present: *unit-tested* pins one request body, one parsed
payload or one refusal, while *offline-harness* pins a run of platform events —
an order advancing through its own state machine, a reconnect resynchronizing,
a start-up sweep reconciling venue state the node did not create.

Three boundaries of that rung, because they decide what the tables below may
say. The harness is an *execution* harness: it drives `GateioExecutionClient`
and nothing else. There is no counterpart on the market-data side — the data
client's offline tests exercise one subscription, one request or one payload at
a time — so **a market-data claim on this page never reads above *unit-tested*
without a run against the venue.** And a product reaches *offline-harness* only
where the harness actually holds an instrument of that product and sends orders
on it; a rung is not inherited from a sibling product that shares the code.

The README's [feature support matrix](../README.md#feature-support-matrix) does
not restate any of this. It answers a narrower question with two glyphs — `✓`
for a capability the offline suite covers, `-` for one the product does not have
— and leaves the evidence question to its **Mainnet** column, which names the
products a recorded run below covered, and to this page.

Five things about how to read those rows.

**Attribution.** The market-data run subscribed spot, USDT perpetual, delivery
and options at once and counted arrivals by data type rather than by instrument,
so every arrival except the mark, index and funding updates is credited to spot
alone — the narrowest reading the record supports, not necessarily the whole of
what arrived.

**Vintage.** The market-data, cancel, quote-denominated-buy, conditional,
perpetual, option and reconciliation runs were made on the released tree. The
lifecycle, the other time-in-force steps and the spot stop-limit step were made
earlier the same day, before the last execution fix landed. That fix changed how
a cash buy completes and how a cancel of an order the venue no longer holds is
reported — and every path it touched was exercised again afterwards, by the
quote-denominated buy and by the cancel steps, each of which opens and closes a
position of its own.

**Checks that do not check what they say.** Three were found while writing this
page, and the rows above state the venue's behavior rather than the check's
verdict wherever they differ. The conditional-order step reads its "accepted
sides" from the cache, which holds orders the platform denied and never sent.
Its trigger-price check reads a field the recorded events do not carry, so it
passes on ten empty values; the orders themselves were submitted with trigger
prices, and the venue accepted them. The cancel-replace check infers a
re-placement from having more acceptances than cancellations, which the
cancellation on stop can make untrue while the re-placements plainly happened —
two runs of identical venue behavior got opposite verdicts from it.

**Failures stand.** A failure is not deleted here because a later run passed,
and two rows above say both things at once. The two whose substance the venue
did deliver — the post-only refusal and the re-armed trigger — keep their failed
verdicts beside what actually happened. A validation record that only keeps its
successes is not a record.

**This is a snapshot.** These rows are what had been recorded when the page was
written, on an account with a fixed budget and a campaign still adding to it. A
row that is absent is a run that had not happened, not a run that was hidden.
Three late steps that would have read state back from the venue — the spot
orders, the short side of the perpetual position, and the option position — are
recorded failed and are deliberately not rows: each ran an hour or more after
the state it was meant to read had been closed or cleaned away, and the venue
answered them with an empty account or a flat position. A step that runs after
its own premise has gone establishes nothing, in either direction.

### What the runs did not confirm

Stated explicitly, because a passing lifecycle invites the assumption that
everything next to it also passed:

* stopping cleanly while a strategy is still quoting — **two of four runs
  failed at this**, as above;
* the batch-cancel route, `_batch_cancel_orders` onto
  `GateioSpotHttpAPI.cancel_batch`, which no live run has reached — the two
  steps meant to exercise it sent a cancel per order instead;
* the sell side of a spot conditional order, which the platform denied for want
  of base currency before it could be sent;
* the conditional-order trigger and fire path — arming, canceling and re-arming
  are confirmed, firing is not, so no run has taken a `GateioTriggerLink` past
  `is_armed` and no fired order id has ever been swapped in;
* any stream on delivery futures or options individually, and every stream on
  inverse perpetuals;
* adoption of a resting **order** into a fresh cache. An open position was read
  back from the venue and adopted, on the perpetual; the order and fill reports
  that accompanied it were answered by the client and then filtered by the
  platform, because no strategy claimed them. What the venue has confirmed is
  that this client reports its state; what no run has confirmed is a resting
  order being taken up and traded on by a node that did not place it;
* restart recovery against the real venue — a node stopping and restarting onto
  its own live state is proven at *offline-harness* only, where
  `generate_mass_status` is driven against a stubbed venue answering with a
  resting order and a trade its own order listing has not caught up with, and
  the position reconciliation above is one half of it;
* every order path on inverse perpetuals and delivery futures; on options,
  everything except the three orders recorded above; and on the USDT perpetual,
  everything except the steps recorded above.

## Why nothing is marked Stable

*Stable* is not a rung on the ladder above, and no rung implies it. The ladder
grades how well one claim is evidenced; *Stable* would be a claim about
repetition — that a path has been shown to keep working, under conditions the
operator did not choose. Several rows above reach *mainnet-confirmed*, which is
as high as the ladder goes. None is called *Stable*, because one recorded run
establishes that a path works, not that it keeps working: no row here has
survived repetition, adverse market conditions, a reconnect or a restart against
the venue. The failed shutdown steps are the argument in miniature — the cancels
went out and were honored, and an order still ended up resting at the venue,
because two seconds of ordinary timing fell the wrong way. Every result on this
page is one sample of behavior that has to hold under conditions no run has yet
imposed on it. *Stable* is reserved for behavior that has been shown to hold,
and the alpha does not claim it.

## Known validation limits

Some paths cannot be validated without account states that are outside the
adapter's control. They are listed here so that "not validated" is never
mistaken for "not attempted":

| Path                                      | Why it is hard to validate                                                                                                                                                                                                                                                                                                                     |
|-------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Cross margin, unified account             | Requires the account to be upgraded out of classic mode; only the account owner can do that, and `GateioMarginHttpAPI.set_unified_account_mode` is never called on their behalf                                                                                                                                                                |
| Unified `multi_currency` mode             | Gate.io requires an account balance above 500 USDT                                                                                                                                                                                                                                                                                             |
| Unified `portfolio` mode                  | Gate.io requires an account balance above 1000 USDT                                                                                                                                                                                                                                                                                            |
| Inverse (BTC-settled) perpetuals          | No testnet endpoint; mainnet validation needs a funded BTC-margined wallet                                                                                                                                                                                                                                                                     |
| Delivery futures                          | No testnet endpoint, and the wallet is created by a first internal transfer. The instrument loads and its subscriptions are accepted; no order has been sent inside this validation's budget                                                                                                                                                   |
| Options beyond one contract               | No testnet endpoint. The contract that was traded had to pass a screen — two-sided book, a spread under a third, open interest, and more than twelve hours to expiry — and its premium had to fit the budget, so the option evidence is one contract wide and says nothing about the rest of the chain                                         |
| Hedge (dual) position mode                | `_assert_one_way_position_mode` refuses it by design and never switches it on, so the refusal is what gets tested, not the mode                                                                                                                                                                                                                |
| Liquidation and auto-deleveraging paths   | Cannot be provoked safely                                                                                                                                                                                                                                                                                                                      |
| Conditional-order trigger and fire        | Requires the market to cross a trigger inside the run; a trigger placed close enough to fire reliably is a trigger that risks an unintended position                                                                                                                                                                                           |
| The sell side of a spot conditional order | A resting sell must be covered by base currency for as long as it rests, so proving it on a cash account means holding inventory across the whole step rather than buying and closing inside it                                                                                                                                                |
| Adopting venue state into a fresh cache   | The platform filters an external order no strategy has claimed (`filter_unclaimed_external_orders`), and reconciles fills only inside its lookback window. Proving adoption needs a node configured to claim the orders and to look back far enough — the run on record was not, so the client's reports are confirmed and the adoption is not |
| Restart recovery                          | Requires resting orders and an open position to be held across a restart on a funded account, which is the one state a bounded validation budget avoids leaving behind                                                                                                                                                                         |

## Reporting a validation result

If you exercise a path against the real venue, a pull request adding a row here
is genuinely useful. Include the date, the product, the instrument, what was
submitted, and what the venue did — including anything that surprised you.
Please do not include account identifiers, order ids, keys or balances.
